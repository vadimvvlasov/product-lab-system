# EXP-ASC-002 — History Search / Text-to-SQL Agent

- **Тип:** product utility / retention; engineering portfolio
- **Статус:** proposed / planned
- **Текущее состояние по README на 2026-10-18:** frontend использует mock data; реальный backend возвращает `501`.

## Основная гипотеза

Пользователям с несколькими сохранёнными договорами нужен способ отвечать на вопросы по своей истории без ручного открытия документов. Функция полезна, если подходящие пользователи запускают поиск, получают корректный ответ по своим данным и повторно используют поиск.

## Почему функция может быть полезна

Она способна повысить utility/retention для активных пользователей, которым нужно находить договоры по условиям. Она не обязательно решает acquisition для новых пользователей, у которых ещё нет истории.

## Минимальный эксперимент

- Ограничить rollout пользователями, у которых есть минимум заданное количество договоров.
- Поддержать небольшой набор понятных аналитических вопросов.
- Начать с read-only запросов; разрешать только `SELECT`, enforce row/column limits, timeout и ownership/tenant filters.
- Проверять SQL до выполнения; не позволять модели самостоятельно менять данные, обходить доступ или раскрывать содержимое чужих договоров.
- Показывать понятный ответ и опционально ссылку на исходные документы/строки.
- При сомнительном запросе задавать уточнение или сообщать, что вопрос не поддерживается.

## Метрики

- `eligible_users` (пользователи, которым доступна функция);
- `history_search_started`;
- `history_search_completed`;
- доля ответов, отмеченных полезными;
- ошибки парсинга/SQL/таймауты;
- повторный запрос и повторное использование через заданный период;
- стоимость и latency на успешный полезный ответ.

Главный сигнал — не количество сгенерированного SQL, а корректный полезный ответ и повторное использование целевой аудиторией.

## Guardrails

- Только данные текущего пользователя.
- Read-only DB credentials при возможности.
- Один ограниченный SELECT, лимит результатов, timeout и allowlist схем/таблиц/колонок.
- Проверка SQL AST/политик до выполнения; нельзя полагаться только на prompt.
- Защита от SQL injection, prompt injection из сохранённого пользовательского текста и раскрытия секретов.
- Не логировать полные SQL-параметры/договоры, если они могут содержать чувствительную информацию.
- Набор тестов на попытки cross-user access и destructive/multi-statement SQL.

## Решение после теста

- Если использование и полезность высоки — улучшать охват, вопросы и UX.
- Если попытки есть, но ответы плохи — улучшать качество/ограничения до расширения.
- Если подходящие пользователи не начинают поиск — проверить обнаруживаемость и реальную потребность.
- Если нет повторного использования и коммерческого сигнала, не считать feature успешной только потому, что агент реализован за день.
