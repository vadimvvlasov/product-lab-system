# EXP-ASC-002: History Search / Text-to-SQL Agent

Тема: product utility / retention. Инженерная ценность (безопасный text-to-SQL agent) — портфельный трек, отчитывается отдельно. Состояние по репо на 2026-10-19: frontend на mock data, `POST /query` возвращает `501`.

## Гипотеза

Пользователям с несколькими сохранёнными договорами нужен способ отвечать на вопросы по своей истории без ручного открытия документов. Функция полезна, если подходящие пользователи запускают поиск, получают корректный ответ по своим данным и повторно используют поиск.

Функция может повысить utility/retention для активных пользователей, которым нужно находить договоры по условиям. Acquisition новых пользователей без истории она не решает.

## Дизайн (G2)

- **Сегмент:** пользователи, у которых есть минимум заданное количество договоров (`eligible_users`).
- **Канал / триггер:** rollout только на этот сегмент; анонс — [[exp-asc-008-feature-post]].
- **Минимальное изменение:**
  - небольшой набор понятных аналитических вопросов;
  - только read-only запросы: `SELECT`, row/column limits, timeout, ownership/tenant filters;
  - SQL проверяется до выполнения; модель не может менять данные, обходить доступ или раскрывать чужие договоры;
  - понятный ответ и опционально ссылка на исходные документы/строки;
  - при сомнительном запросе — уточнение или сообщение, что вопрос не поддерживается.

- **Основное действие:** корректный полезный ответ по своим данным и повторное использование. Главный сигнал — не количество сгенерированного SQL.

- **Метрики:** `eligible_users`; `history_search_started`; `history_search_completed`; доля полезных ответов; ошибки парсинга/SQL/таймауты; повторный запрос и повторное использование через заданный период; стоимость и latency на успешный полезный ответ.

## Риски

- Приватность / security:
  - только данные текущего пользователя;
  - read-only DB credentials при возможности;
  - один ограниченный SELECT, лимит результатов, timeout и allowlist схем/таблиц/колонок;
  - проверка SQL AST/политик до выполнения; нельзя полагаться только на prompt;
  - защита от SQL injection, prompt injection из сохранённого пользовательского текста и раскрытия секретов;
  - не логировать полные SQL-параметры/договоры, если они могут содержать чувствительную информацию;
  - тесты на попытки cross-user access и destructive/multi-statement SQL.
- Качество результата: некорректный ответ по истории.
- Стоимость / latency: на успешный полезный ответ.

## Правила решения (заданы заранее)

- Использование и полезность высоки → `scale`: улучшать охват, вопросы и UX.
- Попытки есть, ответы плохи → `iterate`: улучшать качество/ограничения до расширения.
- Подходящие пользователи не начинают поиск → проверить обнаруживаемость и реальную потребность.
- Нет повторного использования и коммерческого сигнала → не считать feature успешной только потому, что агент реализован за день.
