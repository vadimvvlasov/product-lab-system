# 04. Agentic Delivery: быстрая реализация с coding agents

## Принцип

Coding agent снижает стоимость реализации, но не отменяет продуктовую постановку, верификацию, безопасность и эксплуатацию. Задача человека — выбрать эксперимент, определить границы, проверить результат и решить, что делать по данным.

## Минимальный процесс доставки

1. Создать issue из experiment brief и сослаться на гипотезу.
2. Описать scope, out-of-scope, интерфейс/контракт, критерии приёмки, тесты и метрики.
3. Попросить агента сначала предложить план и назвать неясности; не разрешать ему самостоятельно расширять продуктовую цель.
4. Реализовать небольшой вертикальный срез за одну ветку/PR.
5. Проверить diff, зависимости, секреты, миграции, права доступа, обработку ошибок, таймауты и деградацию.
6. Прогнать тесты: unit, integration/API, e2e для основного пути, negative/security cases по риску.
7. Проверить вручную на dev — в том числе пустые, ошибочные и пограничные состояния.
8. Убедиться, что события аналитики не содержат PII/секреты и совпадают с планом эксперимента.
9. Деплоить по существующему процессу, выполнить smoke test, проверить ошибки и возможность rollback.
10. Записать commit/PR, фактический scope, известные ограничения и ссылки на monitoring/dashboard.

## Защита от «быстрого хаоса»

- Один эксперимент — один основной вопрос; не добавлять попутно unrelated features.
- Не принимать тесты, написанные только агентом, как единственное подтверждение корректности; проверять граничные случаи и исходные требования.
- Не позволять агенту использовать production-секреты или реальную пользовательскую информацию в локальных fixture.
- Для функций с SQL, AI, платежами, конфиденциальными данными или доступом к чужим аккаунтам обязательно проверять authorization, limits, injection и logging.
- Продакшн-мониторинг, rollback и пользовательские ограничения должны быть определены до запуска.
- Отдельно фиксировать портфельные технические задачи, которые не проверяют бизнес-гипотезу.

## Шаблон технической постановки для агента

Передай агенту:

- ссылку на idea/experiment brief;
- точное пользовательское поведение, которое нужно добавить;
- критерии приёмки;
- что не входит в scope;
- существующие архитектурные правила;
- требуемые тесты и команды для их запуска;
- события/метрики;
- риски и security constraints;
- условия, при которых агент должен остановиться и спросить, а не угадывать.

## Definition of Done для экспериментальной функции

Функция считается готовой к эксперименту, если:

- основной сценарий реализован end-to-end;
- критерии приёмки покрыты тестами;
- ошибки и пустые состояния обработаны;
- права доступа и данные ограничены правильным пользователем/тенантом;
- аналитика и источник эксперимента работают;
- guardrail-метрики доступны;
- dev smoke test пройден;
- production rollout и rollback понятны;
- документация отражает фактическое состояние;
- назначено условие review.
