# Owner brief — Coding Agent Workflow Kit

## Цель

Проверить, можно ли превратить проверяемый workflow coding agents в компактный цифровой продукт и получить подтверждённый финансовый сигнал с минимальными затратами. Одновременно использовать сам процесс разработки, проверки и упаковки как тест того, насколько Product Lab System помогает доставлять изменение через роли и независимую QA.

## Два потока — не смешивать

### A. Улучшение Product Lab System

Сначала аудит. В существующей системе уже есть пост-эксперименты, атрибуция, exposure, воронка, revenue/cost, L5 и правила остановки. Потенциальная доработка — только недостающий практический сценарий от гипотезы к посту, квалифицированной экспозиции и реальной оплате, если аудит подтвердит, что такого сценария нет или он неполон.

Не добавлять дублирующие поля, новую сущность, отдельный шаблон или новый scoring без доказанного пробела.

### B. Коммерческий эксперимент

Рабочее название продукта: **Coding Agent Workflow Kit**.

Целевая аудитория-гипотеза: solo builders и разработчики, уже использующие coding agents в существующем репозитории и сталкивающиеся с неполными критериями приёмки, поверхностным самопроверочным QA, scope creep или неясным handoff между постановкой, реализацией и проверкой.

Проблемная гипотеза: им нужен минимальный повторяемый набор файлов и процесса для разделения spec, implementation и independent QA, с понятным repair loop и безопасным handoff.

Предложение-гипотеза: standalone Markdown kit для установки в репозиторий, включая роли/инструкции, шаблон задачи, критерии QA и пример end-to-end прохождения одной небольшой задачи.

Предлагаемая тестовая цена: **$19**. Это предложение для проверки, а не разрешение выставлять цену или брать оплату. Владелец должен отдельно подтвердить конкретную цену и условия checkout перед любым внешним предложением.

## Основная цель первого эксперимента

Проверить реальную готовность целевых пользователей платить за уже доступный, точно описанный kit. Первичная метрика — число подтверждённых оплат целевых покупателей за период эксперимента; clicks, likes, downloads, waitlist и устные обещания — промежуточные сигналы, не L5.

## Ограничения

- Не утверждать гарантированную экономию времени, снижение ошибок или рост автономности без измерений.
- Не продавать обещание будущей недоступной функциональности. Прежде чем принимать деньги, kit должен быть реально подготовлен и доставляем.
- Не публиковать пост, не делать outreach/DM, не менять цену и не настраивать/запускать приём платежей без явного одобрения владельца.
- Не добавлять сложный сайт, SaaS, backend, автоматизированную рассылку, платную рекламу, email automation или несколько ценовых tiers до первых проверенных сигналов.
- Не выдавать технический QA PASS за доказательство спроса.
- Не выдавать один платёж за PMF; он лишь L5-сигнал для ограниченного следующего шага.

## Предпочтительный процесс

Сначала сделать комплект достаточно завершённым, чтобы его можно было честно предложить; затем подготовить один content-led post с `post_goal: pricing` и явным CTA; измерять целевую экспозицию и оплаты по существующим правилам. Если экспериментальная вместимость занята или данных недостаточно, оставить статус draft/ready и описать blocker, не обходить ограничения модели.
