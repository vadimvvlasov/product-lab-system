# System gap audit — content-to-revenue path

## Зачем нужен этот документ

Это не спецификация заранее выбранной фичи. Это guardrail для Explorer/PM: убедиться, что предложение улучшает существующую систему, а не дублирует её.

## Обнаруженные по текущей версии репозитория механизмы

Проверить эти места в рабочей ветке ещё раз перед изменениями — ветка может отличаться от публичного `main`.

| Нужная способность | Уже существующая опора | Вывод для аудитора |
|---|---|---|
| Идея с временем до дохода и затратами проверки | `templates/idea.md`: `test_cost`, `weeks_to_revenue*`, `budget_until`, `budget_signal` | Не добавлять альтернативный набор полей без gap |
| Короткий S-эксперимент и цель поста | `templates/experiment-s.md`: `method`, `post_goal`, гипотеза, primary metric, exposure, attribution и результат | Проверить использование; вероятно, новый шаблон не нужен |
| Полный учёт метрик и денег | `templates/experiment.md`: `exposure`, `primary_result`, `revenue`, `cash_cost_usd`, `spent_hours`, `payment_type`, `refunded` | Не дублировать финансовую модель |
| Правила контентного эксперимента | `system/30-experiment.md`, раздел «Эксперимент-пост» | Проверить, хватает ли примера end-to-end |
| Воронка до монетизации | `system/30-experiment.md`: acquisition, activation, usage, monetization; `qualified_visit → ... → paid` | Не изобретать отдельную воронку, если текущая покрывает сценарий |

| Timebox и правило остановки | `system/00-model.md`, «Правило остановки»; `templates/experiment-s.md` | Использовать текущий timebox; не продлевать задним числом |

## Аудит, который должен выполнить агент

Для каждого требования зафиксировать:

1. актуальный путь и section/heading;
2. что уже описано;
3. сценарий, который всё ещё трудно исполнить без догадок;
4. является ли проблема нехваткой правила, нехваткой примера или просто ещё не созданной записи эксперимента;
5. минимальное решение и почему его недостаточно решить заполнением существующего шаблона.

## Возможный минимальный change (только если gap подтвердится)

Добавить **один worked example** к существующему каноническому документу экспериментов (предпочтительно `system/30-experiment.md`, если это соответствует актуальной структуре), который показывает:

`idea → S experiment (method: post, post_goal: pricing) → готовый выполнимый offer → UTM/CTA → qualified exposure → clicks/leads → confirmed payments/refunds → time/cash accounting → review decision`.

Пример должен ссылаться на уже существующие поля и правила, а не объявлять новые поля каноническими. Он должен явно отличать views/likes/free downloads от L5, включать exposure floor и stop rule до старта и запрещать вывод об отсутствии спроса при недостаточной экспозиции.

Если похожий пример уже существует и достаточен — **не меняй системные файлы**. Сохрани только коммерческий experiment / kit artifacts и отметь audit `no change needed`.

## Не входит в scope

- новый scoring или изменение confidence rules;
- изменение G1/G2/G3/G4, стадий, статусов или шкалы L0–L5;
- новый общий набор полей/отдельный шаблон Content-to-Revenue;
- автоматизация checkout, CRM, email, UTM tracking platform или analytics backend;
- изменение правил оплаты или исключений для предзаказов;
- изменение всей системы на основании одной коммерческой гипотезы.

## QA scenarios

- Можно ли пройти пример, пользуясь только существующими каноническими полями?
- Запрещает ли текст считать likes, views, waitlist или скачивания подтверждённой оплатой?
- Задаются ли `exposure_floor`, `exposure_definition`, `timebox_hours`, review и `stop_rule` до старта?
- Можно ли отличить `more-evidence` из-за недостаточной экспозиции от отрицательного спросового результата?
- Не дублирует ли пример определения в `system/00-model.md` или шаблонах?
