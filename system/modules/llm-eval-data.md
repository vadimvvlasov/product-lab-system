# Модуль: LLM evaluation data

Синтетические данные и проверка качества. Подключается к экспериментам `method: quality` и к метрикам качества результата ([30-experiment](../30-experiment.md)) в продуктах, где LLM классифицирует, извлекает информацию, генерирует ответы или принимает структурированные решения.

## Разделять четыре задачи

1. **Training data:** данные, на которых обучается модель.
2. **Validation data:** для выбора модели, промпта и гиперпараметров.
3. **Gold test set:** фиксированный независимый набор для итогового сравнения.
4. **Production feedback:** случаи, выявленные при использовании пользователями; после проверки они могут войти в будущую версию датасета, но не должны задним числом менять опубликованную оценку предыдущей модели.

## LLM как генератор данных

Синтетические данные особенно полезны для редких категорий, контрастных случаев, перефразирования и стресс-тестирования. Рекомендуемый конвейер:

1. Выбрать реальные/размеченные исходные примеры, где есть право на использование.
2. Сгенерировать вариации условий задачи, стиля и контекста.
3. Генерировать как положительные, так и отрицательные/безопасные примеры.
4. По возможности генерировать контрастные пары, где меняется один ключевой фактор.
5. Требовать структурированный output с меткой, обоснованием и точным evidence span.
6. Автоматически проверять схему, привязку цитаты к исходному тексту, допустимые значения меток, дубликаты и противоречия.
7. Прогнать отдельную модель-критика или независимый verifier; считать это фильтром, а не доказательством истинности.
8. Отбрасывать спорные примеры или помечать их low-confidence.
9. Сохранить происхождение каждого примера и версии генератора.
10. Проверить на gold test set, даёт ли обучение на синтетике реальное улучшение.

## Не допускать утечки

- Не генерировать обучающие примеры из gold test set или из его производных.
- Если тестовый пример происходит из документа, любые близкие фрагменты того же документа должны учитываться при разделении по документам.
- Не подбирать prompt/hyperparameters бесконечно по test set; для итераций использовать validation set.
- Сравнивать baseline и новую модель на том же зафиксированном тесте.

## Метрики

Для классификации: precision, recall, F1 по классам, confusion matrix, false-positive и false-negative rates, calibration/threshold behavior при необходимости. Для извлечения — exact/span match и проверка цитируемого фрагмента. Для генерации — корректность, полнота, groundedness и полезность по заданной процедуре.

При дисбалансе классов не ограничиваться общей accuracy. Публиковать объём набора и правила включения примеров.

## Жизненный цикл качества

Quality-эксперимент проходит те же статусы, что и другие:

1. `draft → ready`: зафиксированы baseline, test set, целевая метрика, пороги, допустимые регрессии, стоимость исполнения и версия evaluation dataset. Без этого G2 не пройден.
2. `ready → live`: eval выполнен на зафиксированном наборе; результаты и сравнение с baseline сохранены в `primary_result`.
3. `live → review`: сравнение с baseline на сопоставимом наборе; проверены регрессии и критические ошибки.
4. `review → closed`: решение `scale` (keep/roll out технического решения в заранее заданном объёме), `iterate` (доработать) или `park`/`kill` (stop/rollback). `scale` здесь не коммерческое масштабирование и не переводит идею в `scaling`; расширение объёма — новый quality-эксперимент.

`evaluated` не отдельный статус: для `quality` его роль выполняет `review` с заполненным `primary_result` и сравнением с baseline. Единого порога улучшения нет: до эксперимента задаются целевая метрика, baseline, допустимые регрессии и цена исполнения. Для критических ошибок — жёсткие лимиты, которые нельзя компенсировать средним улучшением. Сравнение допустимо только на сопоставимом наборе и версии датасета.

Quality PASS доказывает приемлемость технического решения относительно заданных критериев, но не спрос. Коммерческий спрос проверяется отдельным экспериментом; улучшение метрики или публикация не равны коммерческой ценности.

## Человеческая проверка без крупного бюджета

Не обязательно нанимать специалиста на полную разметку всех данных. Возможный минимальный режим:

- сохранить небольшой независимый gold set;
- самостоятельно проверять случайную выборку новых синтетических примеров;
- вручную разбирать все конфликты между генератором и критиком;
- периодически проверять редкие и высокорисковые категории;
- при возможности просить профильного специалиста о разовой проверке наиболее неоднозначной части, а не полной разметке корпуса.

Для high-stakes областей синтетические данные сами по себе не заменяют независимой экспертизы; выводы и пользовательские обещания должны соответствовать качеству валидации.

## Отчёт на каждую версию

Записывать: version/model/prompt, dataset version, число примеров по классам, долю синтетики, происхождение данных, filtering rules, train/validation/test split, основные метрики и сравнение с baseline, ошибки предыдущей модели, новые ошибки, ограничения, решение `scale | iterate | park | kill` и его основание.
